Reporting a security vulnerability

Last updated 23 October 2026

If you think you have found a security vulnerability in this website or its code, please tell us privately so we can investigate and fix it before it is discussed in public. This page explains how to report it, what to include and what to expect from us.

How to report

Report vulnerabilities privately through GitHub private vulnerability reporting on the repository that holds this website’s code. Only you and the repository’s maintainers can see the report, and we can discuss it, and agree on a fix, in the same private thread.

Report a vulnerability privately (opens in a new tab)

You need a free GitHub account to send a report. The link opens a private advisory form on github.com/JosephIwe/buildwise-group-landing-page.

Issues in the live website or its hosting

Use the same private report for problems you find on the live site at buildwisegroup.dev rather than in the code: for example in a page, in the website audit service at /api/website-audit, or in how the site is configured and served. Start the title with “Live site:” and give the exact address you tested. The repository is the source of the live site, so the report reaches the same people either way.

If you can’t use GitHub

Message us on WhatsApp (opens in a new tab) or send a project enquiry that says only that you have a security report and how you would like to be contacted. Do not include any vulnerability details there. Those channels are for ordinary conversations and enquiries, and we will agree a private way to receive the details before you share them.

What to include

  • The affected address, page, API endpoint or file, and the date and time you tested.
  • What the vulnerability is and what an attacker could do with it.
  • Clear steps to reproduce it, with the smallest proof of concept that shows the problem.
  • Any requests, responses or screenshots that support it, with other people’s data removed.
  • Whether you would like to be credited, and the name to use.

Testing guidelines

Please act in good faith and keep any testing to the minimum needed to confirm a problem.

  • Respect privacy. Don’t access, copy, change or delete data that isn’t yours. If you come across personal or confidential information, stop, don’t keep it, and tell us in your report.
  • Don’t disrupt the service. No denial-of-service or load testing, no high-volume automated scanning and no destructive payloads. Keep request rates low.
  • Don’t send test enquiries. Every project enquiry is delivered to a real inbox. If you have found a problem with the form, describe it instead of submitting it repeatedly.
  • Don’t use the website audit against other people’s sites to test it. Point it only at addresses you own or control.
  • No social engineering, phishing or physical attempts against anyone connected with BuildWise.
  • Keep it private until we have coordinated. Please don’t publish or share details before we have had a reasonable chance to investigate and fix the issue, and we have agreed on disclosure with you.

What this covers

  • The website at buildwisegroup.dev and www.buildwisegroup.dev, including the website audit service.
  • The code in the JosephIwe/buildwise-group-landing-page repository.

Services run by other companies that this site uses, such as Cloudflare, Web3Forms, WhatsApp and Google Fonts, are outside this policy. Please report issues in them to those companies directly. Our venture products, such as Huntly, are separate products and are not covered by this page.

How we handle reports

  • We read every report and reply in the private advisory once we have reviewed it.
  • If we can reproduce the issue, we will work on a fix and keep you informed of progress in the same thread. If we can’t, or decide it is not a vulnerability, we will tell you why.
  • We will agree with you when and how the issue is disclosed, which may include publishing a GitHub security advisory once it is fixed.
  • If you would like credit, we will name you in any advisory we publish.

We are a small company and do not run a bug bounty programme, so we can’t offer payment for reports.

Good-faith research

If you follow this page while researching and reporting, we will treat your research as authorised, work with you to understand and resolve the issue, and will not pursue legal action against you for it. This applies only to the systems listed above; we can’t authorise testing of services run by other companies.

Looking to have your own application or cloud setup reviewed? That is a separate service: see our Application & Cloud Security Review. Machine-readable contact details for this policy are in security.txt.
